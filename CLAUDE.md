## What this app is

A web app that grades DECO field-training sessions. A manager uploads an audio recording of a training session; the app sends it to Google's Gemini API, which scores it against DECO's real training rubric and returns section-by-section scores, a total, a certified Yes/No, and written feedback. It also tracks where each field manager stands on their certification path.

**Live at:** https://deco-training-evaluator.github.io

Built as a hackathon project for DECO leadership (judged on Complete / Critical Thinking / Useful, 1–3 each).

## Repo layout

- `index.html` — the entire front end. Single self-contained file: HTML, CSS, and JS inline. Eight tabs: **Dashboard** (certification roster), **Follow-Ups** (see below), plus one per session type — **Training Day**, **Team On-Site Day**, **Conversion Call**, **Stage 1 Interview**, **Reference Checks**, **Stage 2 Interview**. The Reference Checks tab covers two session types (candidate and parent) behind one picker — see its `variants` array.
  - **Follow-Ups (added 2026-08-13)** is the coaching queue: every graded session whose AI verdict came back as anything other than `Certified: Yes`, across all session types, in one filterable list that drains as people tick rows off. Jordan's ask, and the first piece of Phase 4 to actually exist. Design decisions worth not re-litigating:
    - **What pulls a session in is the AI's own `certified` value (column K), nothing re-derived.** So the list can never disagree with the grade on the card.
    - **The reason column splits three things a single "failed" label would flatten:** *scored under 6*, *never came up on the recording* (the audio-only blind spots — counts as 0 by design, not a performance problem), and *the AI wasn't sure* (`needs_human_review`). Keep them separate; that distinction is most of the tab's value.
    - **It's framed as coaching, not a verdict, and must stay that way** while the AI is uncalibrated — same rule as the rest of the app up to Phase 5.
    - **A person's region comes from the Roster, looked up by name** (`regionForPerson`). Nothing region-related was added to the Grading Log; a name that doesn't match the Roster shows as "Region not set" rather than disappearing from the filter.
    - **Someone already certified for that session type gets an "Already certified" flag** — a certified person slipping is a different situation from a trainee who was never expected to pass yet.
    - `fetchSubmissions()` is shared with Recent Submissions so there's one place that knows how sheet rows map onto sessions.
  - **Dashboard rows expand into that person's recordings (added 2026-08-13).** Clicking anyone on the roster opens their sessions inline — every session type, newest first — and each one opens further into the same AI result card (audio player, evidence timestamps) that Recent Submissions and Follow-Ups render. Points worth knowing:
    - **No extra read of the Grading Log.** `fetchSubmissions()` stores its result in `submissionsCache`, and Follow-Ups' load — which already runs on sign-in, on Refresh, and after a grade finishes — then calls `refreshRosterRecordingCounts()` to paint the "N recordings" badges. That's why the badges appear a moment *after* the roster does, and why a row with no badge is still clickable.
    - **`refreshRosterRecordingCounts()` skips the re-render while a row is open**, so a background refresh can't shut a row under someone reading it.
    - **A delete is the one repaint that can't be skipped (fixed 2026-08-13).** Deleting a session from Recent Submissions left it on the Dashboard, because the Dashboard reads `submissionsCache` rather than the sheet and the guard above skipped the repaint — Jordan hit this with a row already expanded. The delete now (a) drops the cleared row numbers out of `submissionsCache` itself instead of waiting on `loadFollowUps()`'s re-read, which can be slow or fail, and (b) calls `renderDashboardKeepingOpenRow()`, which repaints and then re-opens the same person. **The open row is found by name (`data-person`), not by row index** — the index only means something against the filters in effect when the row was drawn — and by comparing the attribute rather than with a CSS selector, since a name can contain an apostrophe.
    - **A delete now proves it worked before the row leaves the screen (2026-08-13).** Jordan deleted a session, watched it disappear from Recent Submissions, and it was still on the Dashboard after a full page reload — so it was still in the Sheet. **What the Sheet actually showed when we finally looked: the manual row empty and the AI row intact.** A session is up to two rows sharing an audio link, and only one of them went; the surviving AI row carries the score and the link, so the session looked untouched. Whether the app cleared one row and reported success on both, or cleared nothing and a later by-hand edit emptied the manual row, was never settled — Jordan resolved it in the Sheet before we could reproduce. Two things made it hard to see, both worth remembering: **the Drive connector serves a *cached* copy of a Sheet** (its `read_file_content` didn't show a row added minutes earlier, while `get_file_metadata`'s `modifiedTime` was live — use metadata to sanity-check freshness, and don't diagnose live data from it), and **the Grading Log had a filter on Trainee Name**, so rows were hidden from the person looking while the API read them all. The delete now (a) renews the token first, (b) reads *every* row back after clearing and treats any surviving data as a failure, keeping the session on screen, and (c) writes the reason into a red bar above the list (`showLogDeleteError`) instead of a button label that says "Delete failed" for three seconds and reverts. A half-deleted session is exactly what the read-back catches, so **the next occurrence will name itself.**
    - Sessions are matched to a person by the **name in column B**, the same name the upload form picked off this roster. A name typed into the Sheet by hand won't match.
    - The person's sessions are **divs, not a nested table** — `#dashboard-table-wrap table` sets `table-layout: fixed`, which would hit any table nested inside it.
  - **Auto-certifying from a manual grade (added 2026-08-13).** A passing manual grade ticks that person's certification column on the Roster and flips the Dashboard badge, with no retyping into the Sheet. This is allowed *because the grade is a human's decision* — an AI grade still never writes to the Roster, and mustn't until Phase 5. Decisions worth not re-litigating:
    - **Both halves of the Smartsheet formula, or nothing.** The form captures one total, and the rule is total ≥ the bar **and every section ≥ 6** — a total can't answer the second half (88/110 with a 4 in one section is not a pass). So there's a **"Every section scored 6 or higher" checkbox** next to the manual grade, and `manualGradeCertifies()` requires it. No tick, no write. The alternative considered and rejected was certifying on the total alone, which would silently certify people the Smartsheet wouldn't.
    - **It only ever writes "Yes".** A grade under the bar leaves the cell alone — a weak session doesn't revoke a certification somebody already holds, and un-certifying is a manager's call, not a form's.
    - **Deleting the grade that certified someone offers to take the certification back — it never does it silently (2026-08-13).** Jordan deleted a passing manual grade and the Dashboard went on saying Certified, because the tick lives on the Roster and the grade lives in the Grading Log; nothing connected the two. Now a successful delete runs `offerUncertifyAfterDelete()`, which rules out every case it can and otherwise puts an amber bar above Recent Submissions with one button (`uncertifyOnRoster` → writes `"No"`). Decisions worth not re-litigating:
      - **It asks rather than writes, because the app cannot know where a "Yes" came from.** It might have been typed onto the Roster by hand, or earned on a session graded before this app existed. Auto-wiping it because an unrelated row was deleted is a worse failure than the one being fixed — and it would contradict the rule directly above.
      - **It's still an offer even though the sections tick is now recorded (column W, below).** W settles one half — a grade recorded as *not* ticked certified nobody, so it no longer produces a pointless offer, and it no longer counts as a remaining grade that holds a certification up. What W can't settle is where an existing "Yes" on the Roster came from: hand-typed, or an older session. `submissionPassedManually()` therefore treats a **blank** W (any row from before 2026-08-13) as *unknown* and still asks. Don't collapse unknown into either answer.
      - **Four gates decide whether the bar appears at all:** the session type has a certification column, the person currently reads certified, the deleted grade was at or above the pass mark, and **nothing left in the Grading Log would certify them on its own** (checked against `submissionsCache` *after* the delete has pruned it, and scoped to the same session type — a Team On-Site Day pass doesn't hold up a Training Day certification).
      - **It writes `"No"`, not a blank.** `certBadge()` reads the two identically, but a written "No" says somebody decided this where an empty cell reads as never filled in.
      - **A failed Roster write keeps the offer on screen with a "Try again" button** and the reason underneath. The delete itself already succeeded and still stands — the two are different Sheets, and the message must not imply the delete came undone.
      - Front-end only. **No `Code.gs` change, no redeploy.**
    - **The sections tick is now written to the Sheet — column W, `All Sections 6+` (2026-08-13).** Jordan looked at a manual-only row reading 89/110 and saw the Certified column showing a dash: *"even though they passed the constraints it does not say certified."* The column only ever reported the AI's verdict (column K), and the log only stored the total — so a grade that certified somebody and a grade that missed on one section were indistinguishable after the fact. The fix was to record the thing the app already knew at submit time. Points worth keeping:
      - **W, not one of the free columns before it.** Code.gs owns A–S; T/U/V are the follow-up state. `GRADING_LOG_LAST_COLUMN` exists so the three ranges that must agree — the read in `fetchSubmissions`, the delete's clear, and the delete's read-back — can't drift apart. **A delete that stops at V leaves an orphaned "Yes" in W.**
      - **The header is written on every submission** (like the follow-up columns write theirs), in its own `try`/`catch`. The grade is already saved by then, and an unlabelled column must never be reported as a failed submission.
      - **The Certified column has three answers for a manual grade, not two** (`manualCertifiedCell`): at/above the bar *and* ticked → **Yes**; under the bar, or recorded as not ticked → **No**; at/above the bar with a **blank** W → **"Bar met"**, a neutral badge whose tooltip says the second half wasn't recorded and points at the Dashboard. Saying "Yes" off the total alone is exactly the shortcut the two-part rule exists to prevent, so **don't make old rows read as certified.**
      - **A session that was AI-graded still shows the AI's verdict** — that column's job during Phase 2 calibration is to show what the AI concluded. The manual verdict fills the cell only when there's no AI grade to show. `certifiedCellFor()` is the one place that decides, shared by Recent Submissions and the expanded roster row so the two can't disagree.
      - Front-end only. **No `Code.gs` change, no redeploy** — Code.gs appends A–S and never reads past S.
    - **Confirmation is inline and *before* submit, not a dialog after it.** `renderCertPreview()` shows what pressing Submit will do to the Dashboard while the score is still on screen and editable — the moment a typo that crosses the bar would actually get caught. A modal a minute later, after the upload, arrives too late to be a real check. It also spells out the *below-the-bar* case, which answers "why didn't it certify?" before it's asked.
    - **The Roster row number is stamped on each person before blank rows are filtered out** (`ROSTER_ROW_NUMBER` in `loadRoster`). Position in `rosterRows` is not the row in the Sheet; one empty row anywhere above someone would shift the write onto the wrong person — and for a certification column, that means signing off somebody who wasn't graded.
    - **The certification column is found by header name, not a hardcoded letter**, so inserting a column in the Roster can't redirect the write onto its neighbour.
    - **The Roster write is a separate `try`/`catch` from the grade write.** They're different Sheets; if the Roster write fails the submission still stands, and the status line says which name to go tick by hand rather than implying the whole submission failed.
    - Only **Training Day** and **Team On-Site Day** have certification columns (`SESSION_CERT_COLUMN`), so the feature is inert on the preview tabs by construction rather than by a special case.
    - Front-end only — the app already holds the `spreadsheets` scope. **No `Code.gs` change, no redeploy.**
  - **Audio is optional on the grading form (2026-08-13).** It used to be `required`, which meant that the moment a passing manual grade could certify somebody, there was no way to actually *use* that — certifying from a paper evaluation with no recording was blocked by the form (Jordan hit this immediately). Now the rule is **audio, a manual grade, or both — but not neither**, since a submission with no recording and no score is an empty row. Consequences that were checked rather than assumed:
    - **Link-less rows don't merge.** `fetchSubmissions()` groups the manual row and the AI row of one session by their shared Audio File Link (column G). Rows with a blank link already went down a separate `noLink` path that keeps each as its own submission — so several audio-less manual grades can't collapse into one. This was the thing most likely to break, and it didn't.
    - **No recording means no AI call**, and the status line says so outright rather than leaving someone waiting for a result that was never coming. No Drive round trip either — the row just carries a blank link.
    - **The Dashboard badge counts "sessions", not "recordings".** Once a session can exist without audio, the old "3 recordings" label would have been overstating what's there to listen to.
    - Every render path (Recent Submissions, Follow-Ups, the expanded roster row) already guarded on a blank `audioLink` and shows N/A or hides the Listen link.
    - **"No audio" is now said out loud, not left blank (2026-08-13).** Hiding the link left an empty gap that reads as "something failed to load" rather than "there is nothing to listen to" — Jordan asked for it after seeing an "Open in Drive" that opened onto nothing. One helper, `audioLinkOf()`, decides it in both views: **only a real `http(s)` link counts as a recording**, so whitespace or a note typed into column G by hand renders as "No recording" (expanded roster row) / "None" (Recent Submissions) instead of as a link with nothing behind it. It also gates `driveFileIdFromLink`, so junk text can't build a player. Note this can't detect the *other* dead-link case — a link whose Drive file was deleted or belongs to an account the viewer isn't signed into — which would need a Drive call per row and isn't built.
  - **Tab order is the real process order, not alphabetical or convenient.** Reference Checks sits between Stage 1 and Stage 2 because that's when references actually get called (Jordan, 2026-08-13). If a new session type is added, put it where it falls in the process.
  - The tab row is generated from a single `SESSION_TABS` array. Each entry is either `status: 'live'` (Code.gs has a rubric for that exact `sessionType` string) or `status: 'preview'` (the tab exists and explains itself but does nothing).
  - **The two live tabs share one grading panel.** `showTab()` re-points `currentSessionType` at the panel rather than there being two copies of the upload form — so the manual-grade cap, the labels, the pill, and which Recent Submissions rows are shown all follow the active tab. Adding a live session type means adding an entry to `SESSION_TABS` and an entry to `SESSION_MAX_POSSIBLE`, nothing more on this side.
  - Because one panel is shared and an AI grade takes ~3 minutes, `gradeSessionWithAI` captures its session type at submit time and refuses to paint progress or results into a panel that has since switched tabs — it shows a "still grading in the background" note on the other tab instead and drops the finished grade into Recent Submissions.
  - **Don't flip a `'preview'` entry to `'live'` just by editing the string.** Code.gs rejects any `sessionType` it has no rubric for; it needs the rubric text, the section keys, the max score, and a redeploy first.
- `apps-script/Code.gs` — the backend. **This is a copy.** The version that actually runs lives inside the Apps Script editor bound to the Grading Log sheet. Editing it here does nothing until it's pasted back in and redeployed (see below).
- `docs/` — the rubrics and reference data the Gemini prompt is built from. **If a rubric or a policy number changes, `docs/` and the prompt text inside `Code.gs` both have to be updated to match.**

## Deploying changes

**Front end (`index.html`):** commit and push to `main`. GitHub Pages redeploys automatically in 1–2 minutes. That's the whole process.

**Backend (`Code.gs`):** editing the file in this repo is not enough. It must be pasted into the Apps Script editor (Grading Log sheet → Extensions → Apps Script), saved, and then **Deploy → Manage deployments → pencil icon → New version → Deploy**. Skipping the New Version step leaves the old code running at the same URL. Label the version to match the file's header (currently V13).

## Rules that matter when changing grading logic

- **BC only.** Everything is scoped to British Columbia. Other provinces are the final phase and explicitly not active work — don't build toward them.
- **Replacements 101 is always graded in BC**, in every territory, never marked N/A. (Confirmed by Jordan; a region-based alternative was considered and rejected.)
- **Certification formulas** must match the Smartsheets exactly:
  - Training Day: total out of 110 across 11 sections; certified = total ≥ 85 **and** every section ≥ 6.
  - Team On-Site Day: total out of 50 across 5 sections; certified = total ≥ 38 **and** every section ≥ 6.
- **A section with no confident score counts as 0**, not as "can't determine." `certified` is always a real Yes/No.
- **Consensus grading:** every session is graded by 3 sequential Gemini calls that get reconciled (median per section). This costs ~3x tokens and ~3x time versus one call — the tradeoff is deliberate, because single calls produced wildly inconsistent scores. Don't "optimize" it back to one call.
- **Passes that fail are survivable, but a degraded result must say so (V11).** A 429 or 5xx on one pass is retried (waiting the delay Google suggests, capped so backoff can't eat the 6-minute budget); a *daily* quota 429 is not retried, because waiting can't clear a daily cap. If a pass still fails, grading proceeds with whatever completed rather than throwing away passes already paid for — but the reviewer notes say how many actually ran, and **a single completed pass flags every section for human review**. That last part matters: `reconcileSection` can't detect disagreement it never saw, so one uncorroborated pass would otherwise produce a confident-looking score with nothing behind it.
- Because grading is 3 sequential calls, a long recording can approach Apps Script's 6-minute web app limit. If timeouts appear, either lower `GRADING_RUNS_PER_SESSION` to 2 or restructure as parallel `UrlFetchApp.fetchAll` calls.
- **Evidence timestamps (V10).** Every section returns `evidence_clips` — 1–3 `{at, quote}` moments pointing at the audio that drove its score — and the results card turns those into clickable jump points on an in-page player. The point is that a flagged section can be checked in about a minute instead of by re-listening to the whole session. These are an aid to a human's judgement, **not** citations. Don't present them as exact anywhere in the UI.
- **Measured timestamp accuracy — 2026-08-13, the only real measurement so far.** Jordan hand-checked all 5 citations from a 2:22 test clip against the audio. Cited 0:07 / 0:28 / 0:43 / 0:55 / 1:43; the matching exchanges start at 0:11 / 0:32 / 0:43 / 0:58 / 1:43. **Off by 0–4 seconds, always slightly early, never late.** The feature works.
- **HOW TO VERIFY A TIMESTAMP — read this before concluding they're broken.** Check a citation against **where that topic starts**, not against a specific phrase inside it. The prompt tells Gemini to point at where an exchange *begins*, so measuring against a line spoken later in the same exchange makes it look badly late when it isn't. This exact mistake was made on 2026-08-13: two citations looked ~23s off and were written up as an uncorrectable "clock slip", with an elaborate silence-in-the-audio theory attached. Both were correct — 0:43 was checked against the pickle line at 1:07 when it was pointing at "is three things DECO" (the pillars) at 0:43 exactly, and 1:43 was checked against the VIP package at 2:06 when it was pointing at "if they have damage", where the replacement discussion opens. Don't rebuild that theory; measure properly instead.
- **Corrections are the fix-list, not a second Focus Areas (V13, 2026-08-13).** Jordan's point: a Training Day runs over two days and the recording gets submitted while there's still time left with the Site Operator, so the card was missing the one thing a trainer needs in that moment — what to go back over before the session ends. Each entry is `{section, issue, correct, at, priority}`: what was actually said or skipped, what it should be per the rubric/reference data, where to hear it, and `must_fix` vs `should_fix`. Things that matter:
  - **The prompt has to say explicitly that this is not `focus_areas`** (Code.gs rule 9). Focus areas are for the *next* session; corrections are for *this* one, before it's over. Without that line Gemini returns the same list twice.
  - **An entry with no timestamp is an omission, and those are the valuable ones** — something that never came up at all still needs covering before the day ends. The card labels those "never came up" / "Missing" instead of "Heard", rather than just showing no jump point.
  - **An unrecognised or missing `priority` renders with no badge**, not a guessed one. The page must not claim an urgency the AI never assigned.
  - **Half a correction is dropped, not shown.** An entry missing either the issue or the fix can't be acted on, and a to-do row nobody can act on is worse than one fewer row.
  - Capped at 6, `must_fix` first — it's a list somebody works through in the hours that are left, not a report.
- **`CLIP_PREROLL_SECONDS` is 3.** Citations run 0–4s early already, so playback only needs a few seconds of run-up. The original 10 was guesswork and just added dead air before the exchange. The ±15/+30 nudge buttons on the player stay useful regardless — the cited moment is the *start* of a topic, so the specific line a manager wants is usually a little further in.
- **Sections with more than one timestamp (2026-08-13).** A section can carry up to 3 moments, and three bare times (`00:34 02:15 07:41`) gave a manager nothing to choose between without hovering each one. So:
  - **One clip renders exactly as before** — a compact time chip, quote in the tooltip. **Two or more stack**, each with the first 5 words of its quote underneath. The split is deliberate: there's nothing to tell apart when there's only one, and a quote line on all 11 sections would undo the card's 2026-08-13 tightening. Measured at 1280px: a 3-clip section grows the row to ~294px, a 1-clip section stays at 160px.
  - **A moment two or more passes independently landed on says so in words, under the chip: "2 passes point here".** `mergeClips` always counted this (it's how it ranks when a section is over the 3-clip cap) and then dropped it before rendering, so a moment all 3 passes flagged looked identical to one a single pass mentioned. The count says *where to start listening is a better bet*, *not* that the score is more right — the footnote says so.
  - **This shipped first as a compact `×2` / `×3` badge on the chip and that was wrong.** Jordan read `1:42 ×2` on sight as "there are 2 timestamps to review here" — the exact opposite of its meaning, since a corroborated clip is ONE moment several passes agreed on. Any small glyph next to a number invites that reading. **Don't reintroduce a badge here; the count gets plain words or it doesn't ship.** The footnote now leads with the distinction (one moment vs. several) rather than just defining the marker.
  - **The count is never shown as a fraction.** A degraded grade (V11) can run on fewer than 3 passes, so a printed denominator would sometimes be a lie.
  - **This was front-end only — no `Code.gs` change, no redeploy.** Both copies of `mergeClips` already emit `runs`; only rendering changed. The 158px score column is why quotes are cut to 5 words with a 2-line CSS clamp behind them.
  - Still unaddressed: if more than 3 distinct moments survive merging, the extras are dropped with nothing on screen saying so.
- **Still untested at length.** All measurement so far is from one 2:22 clip. Whether accuracy holds across a 60-minute session is genuinely unknown — check one citation near the start and one near the end of the first real session, using the verification method above. If accuracy degrades badly over a long recording, the honest response is to stop rendering a clickable time and show only the quote, so a manager searches for words instead of trusting a number that lies.

## Known quirks worth knowing before you debug

- **Corrections have no sheet column, and that's deliberate.** The `corrections` fix-list (V13) rides along inside column S's raw JSON and gets rebuilt by `correctionsFromRuns()` in `index.html`, exactly like evidence clips. It has no column of its own because T/U/V now belong to the follow-up state — a 20th column appended by `Code.gs` would land on top of `Follow-Up Status`. Both sides take corrections from the **last completed run** (they're prose, not scores) and both sort by **priority only**, relying on a stable sort to preserve the AI's own ordering inside each priority. Change one side's ordering and a session's fix-list will reorder itself depending on whether it was freshly graded or re-opened from the log.
- **Columns T through W of the Grading Log are the front end's, not Code.gs's.** Follow-up state (`Follow-Up Status` / `Follow-Up Note` / `Follow-Up Date`, T/U/V) is written onto the **AI row**, and the sections tick (`All Sections 6+`, W) onto the **manual row**, by `index.html` alone. Code.gs appends 19 columns (A–S) with `appendRow` and never reads or writes past S, so neither the Follow-Ups tab nor the sections tick needed **any backend change or redeploy** — and mustn't be given one by accident. Two things to keep in step: `ensureExtendedHeaders` in Code.gs only writes headers when `Source` is missing (so extra columns don't confuse it), and **deleting a submission clears out to `GRADING_LOG_LAST_COLUMN`, not `A:S`** — stopping short leaves the Follow-Ups tab a ghost row or the Sheet an orphaned tick.
- **Column S of the Grading Log holds all 3 raw runs concatenated**, separated by `----- next run -----` — not one clean JSON object. `index.html` has a `parseAiResultFromRow()` function that handles both that format and the older single-JSON format. Optional future cleanup: have `Code.gs` also write one reconciled JSON object so the front end doesn't need to rebuild it.
- **Because of that, reconciliation logic is deliberately duplicated in two places** — and has to stay in sync. A freshly graded session gets its reconciled sections from `Code.gs`; the same session re-opened from Recent Submissions gets them rebuilt in `index.html` from those raw runs. `parseClipSeconds` / `formatClipTime` / `mergeClips` and the `SCORE_SPREAD_FLAG_THRESHOLD` constant exist in both files. Change one, change the other, or a session will look different depending on how it was opened. (This bit before: the front end's rebuild used to collapse every non-unanimous section into a plain "insufficient evidence", so the `†` and Double-check flags silently vanished from any session re-opened from the log. Fixed in V10.)
- **Gemini quota and cost — this caused a confusing failure once.** The API key was on Gemini's **free tier: 20 `generate_content` requests per day** for `gemini-3.5-flash`. Consensus grading spends **3 per session**, so that's ~6 sessions a day, and a day of testing exhausts it. When it runs out, the page shows **"AI grading request failed: Failed to fetch"**, which looks like a network or CORS problem and is not — the real error (HTTP 429) is only visible in **Apps Script → Executions**. Always check that log before theorising. Cost on the paid tier: audio bills at 32 tokens/second, so a 60-minute session is ~115k tokens per pass and ~345k across 3; at $1.50/1M in and $9.00/1M out that's **roughly $0.63 a session**. Fixed by enabling billing on the API key's Google Cloud project (AI Studio → API keys → the project → Set up Billing). **Except it evidently wasn't, or didn't stick — the V13 test run on 2026-08-13 hit the daily cap again** ("Only 2 of 3 AI passes completed - Gemini daily quota is used up" in the reviewer notes). Confirm billing is actually active on the project that owns the key before booking any further testing; a half-completed consensus grade is a weaker result than it looks.
- **Testing costs real money now.** Use a short clip (2–5 minutes) for anything that only exercises plumbing — whether timestamps render, whether the card parses, whether a deploy took. A 5-minute clip is ~1/12 the cost of an hour-long one and tests the mechanism just as well. Save full-length sessions for actual calibration work, where the grade itself is the point.
- **` | ` is a structural separator, not punctuation.** `notes_for_human_reviewer` is one long string that `index.html` splits on ` | ` to render bullets. Anything appended to it — including error text from a failed pass — must not contain ` | ` internally, or one note shatters into several nonsense bullets. This bit V11 on its first live run, when raw Google error JSON was appended after a ` | raw: ` marker.
- **Raw API responses belong in Apps Script → Executions, never on the results card.** `callGemini` logs the full failure response there; the message that reaches a manager is a plain sentence. When debugging, that log is the source of truth.
- **Apps Script Web App access must be set to "Anyone", not "Anyone within decorepair.com".** The domain-restricted setting breaks CORS when called via `fetch()` from GitHub Pages, even though the endpoint works fine when opened directly in a browser. This cost real debugging time once — don't change it back.
- **Sign-in can't be made permanent.** This is a client-only Google auth flow; tokens last ~1 hour and are silently renewed in the background, but that renewal depends on the browser's own Google session. Truly indefinite sign-in would need a backend holding a refresh token. Don't promise more than that.
- The progress bar during AI grading is an **estimate**, not real server progress — Apps Script is one blocking call with no progress feed. The UI says so explicitly. Keep it honest.
- OAuth client ("Training Tracker Web") is **User type: Internal**, so any @decorepair.com account can sign in with no verification screen. Authorized origins include both `https://deco-training-evaluator.github.io` (current) and `https://decomancer128.github.io` (the original personal-account URL).
